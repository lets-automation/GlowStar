# Deployment Documentation

**For:** Glow Star IT
**From:** Lets Automation
**Purpose:** every script that will run on your server, what each line does, and
how it was tested — so your team can review it before it runs on your machine.

> **One specification note:** please order **Ubuntu 24.04 LTS**. Testing showed
> 22.04's `python3.11` package is a release candidate (`3.11.0rc1`) and it ships
> PostgreSQL 14; 24.04 gives stable Python 3.12.3 and PostgreSQL 16, and is
> supported to 2029 rather than 2027. Everything below was verified on 24.04.

## 1. What gets installed

Four files, all in `deploy/`. Nothing else is added to your machine.

| File | What it is | Runs |
|---|---|---|
| `install.sh` | One-time provisioning | Once, by hand, at setup |
| `glowstar-api.service` | The pricing API definition | Always (restarts on failure) |
| `glowstar-nightly.service` + `.timer` | The nightly data + retrain job | 02:30 daily |
| `backup.sh` | Backup job | Nightly, at the end of the above |

They are plain text. Your team can read all four in about ten minutes — that is
deliberate, and why we did not use a container or an opaque installer.

## 3. `install.sh` — the one-time setup

Run once, as root, on the new server: `bash deploy/install.sh`

### 3.1 System packages

```bash
apt-get install -y python3 python3-venv python3-pip \
    postgresql postgresql-contrib nginx certbot python3-certbot-nginx \
    sqlite3 git curl sudo gzip tzdata rclone
```

| Package | Why |
|---|---|
| `python3`, `python3-venv`, `python3-pip` | The engine (Python 3.12 on 24.04) |
| `postgresql`, `postgresql-contrib` | The database (v16 on 24.04) |
| `nginx` | HTTPS front door |
| `certbot` | Free, auto-renewing TLS certificate |
| `sqlite3` | Local backup format, diagnostics |
| `git`, `curl` | Deployment and health checks |
| `sudo`, `gzip` | Used by the script itself |
| `tzdata` | Timezone data — the server must run on India time, see 4.2 |
| `rclone` | Sends the nightly backup to off-site storage |

Nothing else is installed. No Docker, no runtime we do not control.

### 3.2 Service account

```bash
useradd --system --create-home --shell /usr/sbin/nologin glowstar
```

The application runs as **`glowstar`**, never as root. `--shell /usr/sbin/nologin`
means **nobody can log in as this account** — if the API were ever compromised,
the attacker gets a user that owns one directory and cannot open a shell.

### 3.3 Database creation

```bash
sudo -u postgres psql -tc "SELECT 1 FROM pg_roles WHERE rolname='glowstar'" | grep -q 1 || \
  sudo -u postgres psql -c "CREATE USER glowstar WITH PASSWORD '${GS_DB_PASSWORD}';"
sudo -u postgres psql -tc "SELECT 1 FROM pg_database WHERE datname='glowstar'" | grep -q 1 || \
  sudo -u postgres psql -c "CREATE DATABASE glowstar OWNER glowstar;"
```

Reads as: *"if this role does not already exist, create it."* Running the script
twice is safe — **tested, no duplicate and no error**.

The password comes from the environment (`GS_DB_PASSWORD`), never hard-coded.

### 3.4 Python environment

```bash
sudo -u glowstar python3 -m venv /opt/glowstar/.venv
sudo -u glowstar /opt/glowstar/.venv/bin/pip install -r requirements.txt
```

A **virtual environment** — a private, isolated copy of Python inside
`/opt/glowstar`. Our libraries cannot affect anything else on the server, and a
system update cannot break us. `requirements.txt` pins exact versions, so the
install is repeatable.

### 3.5 Preflight — the Rapaport list must be present

```bash
for f in CSV2_ROUND_8_4.csv CSV2_PEAR_8_4.csv; do
  [ -s "$APP_DIR/$f" ] || { echo "  MISSING: $f"; missing=1; }
done
[ "$missing" = "1" ] && exit 1
```

The Rapaport price list has no live feed — you send us the CSV, and it ships with
the application rather than being downloaded. The script therefore checks it is
on disk and **stops if it is not**, before any service is started.

This is deliberate: without it the API would start normally and `/health` would
return 200, and only the first actual price request would fail. Better to fail
during installation, while somebody is watching.

### 3.6 What the script deliberately does NOT do

It stops and prints five remaining steps rather than guessing:

1. Put credentials in `.env` (secrets must be entered by a human)
2. Obtain the TLS certificate (needs your domain name)
3. Load the initial data
4. Verify with `curl localhost:8000/health`
5. **Verify an actual price** — `/health` returns 200 even when pricing is not
   working, so the last check asks the service for a real quote:

```bash
curl -s -X POST localhost:8000/price -H "X-API-Key: $GS_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"Shape_full":"ROUND","Weight":1.01,"Color":"G","Clarity":"VS1"}'
```

## 4. Service definitions (systemd)

systemd is Ubuntu's standard service manager. It starts things at boot, restarts
them on failure, and keeps the logs.

### 4.1 The API — `glowstar-api.service`

```ini
[Service]
Type=exec
User=glowstar
WorkingDirectory=/opt/glowstar
EnvironmentFile=/opt/glowstar/.env
ExecStart=/opt/glowstar/.venv/bin/uvicorn glowstar.service.app:app \
          --host 0.0.0.0 --port 8000 --workers 2 --timeout-keep-alive 65
Restart=always
RestartSec=10
MemoryMax=6G
```

| Line | Meaning |
|---|---|
| `User=glowstar` | Never root |
| `EnvironmentFile` | Secrets from a file readable only by this user |
| `--workers 2` | Two copies to handle simultaneous requests. **Not more:** each holds its own copy of the model (~1 GB), so more workers cost memory without adding speed — this workload is model-bound, not request-bound. |
| `Restart=always` / `RestartSec=10` | If it crashes, restart after 10 seconds, forever |
| `MemoryMax=6G` | A hard ceiling. If the API ever leaked memory it would be killed and restarted rather than starving the nightly rebuild. |

**Logs:** `journalctl -u glowstar-api -f`

### 4.2 The nightly job — `.service` + `.timer`

```ini
# glowstar-nightly.service
ExecStart=-/opt/glowstar/.venv/bin/python -m glowstar.ingestion.run_snapshot
ExecStart=/opt/glowstar/.venv/bin/python -m glowstar.training.retrain
ExecStart=/opt/glowstar/deploy/backup.sh
TimeoutStartSec=4h
```

Three steps in order: **fetch fresh data → rebuild and test the model → back up.**

The **`-`** before the first command means *"continue even if this fails"*. That
is deliberate: if the data pull fails, we still want the retrain and the backup to
run rather than skipping the whole night.

```ini
# glowstar-nightly.timer
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=300
```

| Line | Meaning |
|---|---|
| `OnCalendar` | 02:30 every day, **India time** — see the note below |
| **`Persistent=true`** | **If the machine was off at 02:30, run as soon as it starts.** This is the single most important line: a missed night means a stale price grid, and stale grid data costs ~3 points of accuracy. |
| `RandomizedDelaySec=300` | Spread start by up to 5 minutes, so we never hit your APIs at exactly the same instant every day |

**Server timezone — set during installation.** Azure's Ubuntu images default to
**UTC**, and this schedule uses the server's *local* time. On a UTC server
"02:30" would fire at **08:00 India time** — the middle of your working day,
competing with live pricing requests. The installer therefore sets the server to
**Asia/Kolkata** and **refuses to continue if that did not take effect**, so the
job cannot silently end up running at the wrong hour. Your grid data is stamped
in India time too, so this keeps the whole system on one clock.

**Verified:** systemd's own validator accepts all three files, and the timer
resolves to the correct next run.

**Logs:** `journalctl -u glowstar-nightly`
**Status:** `systemctl list-timers glowstar-nightly`

## 5. The backup job — `backup.sh`

Runs at the end of every nightly job.

### 5.1 What it saves, and why each matters

```bash
# 1. the irreplaceable grid history
gzip -c /opt/glowstar/data/master_grid/history.json > "$BACKUP_DIR/grid_history_$STAMP.json.gz"

# 2. the database
pg_dump "$GS_DATABASE_URL" | gzip > "$BACKUP_DIR/db_$STAMP.sql.gz"

# 3. the feedback log
cp .../decisions.jsonl "$BACKUP_DIR/decisions_$STAMP.jsonl"
```

| # | What | Recoverable if lost? |
|---|---|---|
| 1 | **Grid history** | **NO.** This records what every cell of your price grid read on every past day. Your grid API only serves a short recent window, so a day that passes unrecorded is gone permanently — and without it the pricing model cannot be honestly tested. **This is the one irreplaceable file in the system.** |
| 2 | Database | No — every price quoted and every desk decision |
| 3 | Feedback log | Duplicate of the database, kept as a plain-text safety net |

### 5.2 Retention and off-server copy

```bash
find "$BACKUP_DIR" -name '*.gz' -mtime +30 -delete
```

Keeps 30 days locally; older files should already be off the machine.

```bash
az storage blob upload-batch -d backups -s "$BACKUP_DIR" ...
```

Copies to Azure storage if `GS_BACKUP_AZURE_URL` is set. **A backup on the same
disk is not a backup** — if the disk fails you lose both. This is the one thing we
need from you that we cannot provide ourselves.

### 5.3 Verified by restoring, not by looking

We did not just check that a file appeared. On the test machine we took a backup,
created an **empty** database, restored the dump into it, and read the row back:

```
restored row: S26-10545 -47.6
```

All three tables were present in the dump. **A backup that has never been
restored is not a backup.**

## 6. Self-hosted PostgreSQL

### 6.1 Why self-hosted rather than a managed service

| | Self-hosted (recommended to start) | Azure managed |
|---|---|---|
| Cost | included in the server | +$50–80/month |
| Backups | our nightly job (tested) | automatic |
| Patching | we apply with OS updates | automatic |
| Suitability | **more than adequate** at this volume | overkill today |

Our write volume is a few thousand rows a day. PostgreSQL handles that on modest
hardware without noticing. **You can move to managed later without any code
change** — one connection string, nothing else. If you would rather not depend on
us for backups and patching, take managed from day one; that is a legitimate
choice.

### 6.2 Configuration

- **Listens on localhost only.** The database is not reachable from the network;
  only the application on the same machine can connect. Nothing to firewall.
- **One user, one database.** `glowstar` owns `glowstar` and nothing else.
- **Password from the environment**, never in a file in the repository.
- **Version 16** on Ubuntu 24.04 (the distribution default).

### 6.3 What is stored

| Table | Contents |
|---|---|
| `quotes` | Every price published: stone, discount, $/ct, the confidence range, and **which model version produced it** |
| `decisions` | Every accept / reject / override, the variance, and the reason where one was required |
| `scores` | The AI score components, so the scoring can be improved later against what stones actually did |

The schema is created automatically on first start and is safe to re-run.

### 6.4 If the database goes down

**Pricing continues.** Every database write is best-effort: if the store is
unreachable, the desk still gets its price and we lose an audit row (recoverable)
rather than the quote (not). Failures are logged loudly, and `/health` reports
`degraded`.

This is tested — there is an automated test that simulates a dead database and
asserts that pricing still returns a number.

### 6.5 Routine commands

```bash
# size
sudo -u postgres psql -c "SELECT pg_size_pretty(pg_database_size('glowstar'));"

# manual backup
pg_dump "$GS_DATABASE_URL" | gzip > /tmp/manual.sql.gz

# restore
zcat backup.sql.gz | psql "$GS_DATABASE_URL"
```

## 8. Your questions, answered

### 8.1 How the domain is set up on Linux

Three steps. Only the first is on your side.

| Step | Who | What |
|---|---|---|
| 1 | **You** | Create a DNS **A record** — e.g. `pricing.glowstar.com` pointing at the server's public IP address. About five minutes wherever your DNS is managed. |
| 2 | Us | Put that name into nginx (it is currently a `YOUR_DOMAIN` placeholder). |
| 3 | Us | Run `certbot --nginx -d pricing.glowstar.com`. This obtains a free certificate and installs a timer that renews it automatically. |

Your CRM then calls one address — `https://pricing.glowstar.com`. Plain HTTP
redirects to HTTPS, so a price is never sent unencrypted.

> **⚠️ Please read this one before locking down the firewall.**
> The free certificate is renewed by an automated check that makes an **inbound
> request to port 80 from the public internet**. If port 80 is restricted to your
> office addresses only, the *first* certificate still works — and then the
> **automatic renewal fails about 60 days later and the API stops answering.**
>
> Three ways to avoid it, any of which is fine:
> 1. Leave **port 80 open to the internet**. It only ever issues a redirect and
>    serves no data. (Port 443 can still be restricted.)
> 2. We use **DNS-based validation** instead, which needs no inbound access at
>    all — this requires an API credential for your DNS provider.
> 3. **You supply your own certificate** (e.g. a corporate wildcard) and we
>    install it. Then Let's Encrypt is not involved and you control renewal.
>
> Tell us which you prefer and we will set it up that way from day one.

### 8.2 Should backups go to a different server?

**Your instinct is correct** — a backup sitting on the same machine is not a
backup. But a second *server* is the most expensive way to fix it. Three options,
best first:

| Option | Cost | Inbound firewall openings | Notes |
|---|---|---|---|
| **Azure Blob Storage** (recommended) | ~$5–15/mo | **none** | Already built (section 5.2). The nightly job pushes the files out over HTTPS. Nothing to patch, nothing to manage. |
| A second virtual machine | another full VM | one, on the second machine | Works, but you now run and patch two servers instead of one. |
| Copy into your own building | — | see below | Do it the safe way, described next. |

**If you want a copy inside your own network**, please do **not** have our server
push into it — that requires opening your firewall inward, which is exactly what
you are trying to avoid. Instead, have **your** machine *pull* the files from
Azure Blob Storage on a schedule. That is outbound-only on both sides and opens
nothing.

**Our recommendation:** Azure Blob Storage as the off-site copy, and if your
policy also wants a copy in-house, your machine pulls from it nightly.

Two things worth knowing:

- The one genuinely **unrecoverable** file is `history.json` — the day-by-day
  record of what your price grid read. Your grid API only serves a short recent
  window, so a day that passes unrecorded is gone permanently (section 5.1).
- A backup only counts if a **restore** has been proven. We tested restoring into
  an empty database and got the data back (section 5.3).

### 8.3 Should we use MSSQL instead of PostgreSQL?

**It is technically possible.** We checked rather than assumed: our database
schema compiles cleanly for SQL Server, and the only genuinely PostgreSQL-specific
thing in the whole system is a single line in the backup script.

**We still recommend PostgreSQL**, for three reasons:

1. **Licence cost.** SQL Server needs a paid licence; PostgreSQL does not. That is
   a permanent cost for a database holding three modest tables.
2. **PostgreSQL is the tested path.** Installation, backup and restore have all
   been run and verified on it (section 2). Moving to SQL Server means roughly
   **2–3 days** to switch drivers, change the backup command and re-test
   everything.
3. **If you mean your existing in-house SQL Server, that is a much larger
   change.** Our server would have to reach *into* your network for every write.
   That converts a design that needs no inbound access into a VPN project, and
   makes every price request depend on that tunnel staying up.

**Before deciding, it is worth checking what is actually driving the question:**

| If the reason is... | Then... |
|---|---|
| Company policy requires Microsoft SQL | **Azure SQL Database** (managed, in the same cloud) is the sensible compromise — not your in-house server. |
| Your team only supports SQL Server | A fair reason. We will do it; please allow the extra 2–3 days. |
| **"Our reporting tool needs to read this data"** | **Then no database change is needed at all.** We can provide a read-only login or a nightly export. In our experience this is usually the real requirement. |

### 8.4 Your systems are in-house and secured — how will the requests work?

There are two directions here, and they are easy to conflate. Only one of them
involves your network.

**Direction A — your CRM calls us. This is the main flow.**

Your CRM makes an ordinary **outbound HTTPS request** to our address, exactly like
any other external API your systems already use. Authentication on our side is
**one header**:

```
X-API-Key: <the key we give you>
```

That is the whole mechanism. **No Active Directory, no domain login, no client
certificate**, and nothing for your internal security to authenticate against —
from your network's point of view we are simply an external HTTPS endpoint you
call out to.

You would only see an "unauthorized" (`401`) response if that header is missing or
mistyped, which is entirely within your control. If you run an outbound proxy with
an allowlist, add our domain to it.

**Direction B — us reading your data.**

Worth stating plainly: **we do not need to enter your network.** All three sources
we read are public internet addresses:

| Source | Address |
|---|---|
| Inventory + sales | `channelpartnerapi.azurewebsites.net` (your own Azure-hosted API) |
| Price grid | `pricingapi.diamanto.co` |
| Market comparables | `app.uni.diamonds` |

**If any of these is moving in-house, please tell us** — that genuinely changes the
design and we would need to plan a VPN or a published endpoint.

**Extra protection we can add if your security team wants it:**

| Option | What it does |
|---|---|
| **IP allowlist** | Our API accepts requests only from your server's public IP address. Strong, and costs nothing. |
| **Mutual TLS** | Your CRM presents a client certificate in addition to the API key. |
| **Static outbound IP** | We fix our server's outgoing address so you can allowlist us in your own firewall. |

## 9. Azure — sizing and pricing

The specification in SERVER.md is unchanged: **4 vCPU / 16 GB RAM / 256 GB SSD**,
which on Azure is a **`D4s_v5`** (or `D4as_v5`, the AMD equivalent — same size,
usually slightly cheaper).

Price it yourself here, rather than taking our estimate:

| What | Link |
|---|---|
| **Azure pricing calculator** (build the exact configuration) | https://azure.microsoft.com/en-us/pricing/calculator/ |
| **Linux Virtual Machines** price list | https://azure.microsoft.com/en-us/pricing/details/virtual-machines/linux/ |
| **Managed disks** (the 256 GB SSD) | https://azure.microsoft.com/en-us/pricing/details/managed-disks/ |
| **Blob storage** (off-server backups, section 5.2) | https://azure.microsoft.com/en-us/pricing/details/storage/blobs/ |
| *If you later prefer managed PostgreSQL* | https://azure.microsoft.com/en-us/pricing/details/postgresql/flexible-server/ |

**To reproduce our estimate in the calculator:** add *Virtual Machines* → region
**Central India** (or wherever your Channel Partner API sits) → OS **Linux** →
size **D4s_v5** → **256 GB Premium SSD**. Then add *Storage Accounts* → **Blob**
→ ~50 GB for backups.

Two things worth knowing before you order:

- **Pay-as-you-go is the price shown. A 1-year reserved instance is roughly
  30–40% cheaper** for the same machine. This server is not a temporary
  experiment — it runs nightly, permanently — so a reservation is worth
  considering once you are satisfied with the setup.
- **Choose Linux, not Windows, in the calculator.** The Windows Server licence is
  bundled into the hourly rate and is the ~40% difference discussed in SERVER.md
  section 4.

Prices change and vary by region, so please treat our `$140–170/month` as an
estimate and confirm with the calculator or your Microsoft account team.
